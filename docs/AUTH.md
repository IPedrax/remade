# GitHub authentication

Remade's directory stays static at `https://remade.wiki`. The Rust Worker in `apps/backend/remade-api/` serves only login, callback, account lookup and logout at `https://api.remade.wiki/api/v1/auth/`. GitHub authenticates identity; UUIDv7 values generated by Remade identify users independently of their GitHub IDs. D1 is the shared Remade application database; the initial schema supports authentication and can be extended with future numbered migrations for features such as upvoting. There are no account roles, votes or publishing permissions in this milestone.

The backend comes from Cloudflare's official workers-rs `templates/hello-world` template. It uses worker 0.8.7, worker-build 0.8.7, Rust 1.99.0 and root pnpm-managed Wrangler 4.149.0. Commit the backend Cargo.lock and root pnpm-lock.yaml. See [Cloudflare's Rust guide](https://developers.cloudflare.com/workers/languages/rust/) and [GitHub's OAuth flow](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps).

The header uses Sonner to confirm successful sign-in with “Logged in as [GitHub username]” and successful sign-out with “Logged out”. A short-lived session-storage marker survives the OAuth redirect so returning page loads do not repeat the sign-in toast. Toasts appear only after the API confirms success; unavailable browser storage does not block login.

The header authentication controls are currently enabled only during development (`import.meta.env.DEV`). Production builds hide them until the login rollout is enabled. Local React and Worker integration tests remain available; production E2E account flows are temporarily marked pending.

## Local development

Install prerequisites once:

```sh
pnpm install --frozen-lockfile
rustup toolchain install 1.99.0 --component rustfmt --component clippy --target wasm32-unknown-unknown
cargo install worker-build --version 0.8.7 --locked
```

Create a separate development **GitHub OAuth App** with homepage `http://localhost:4321` and callback `http://localhost:8787/api/v1/auth/github/callback`. It is separate from the GitHub App used for catalog metadata. Copy `apps/backend/remade-api/.dev.vars.example` to `.dev.vars` in the same directory and fill in your development client ID and secret. The file is ignored; never commit its contents. The example overrides both origins to localhost.

```sh
just backend::migrate-local
just backend::dev
```

The Wrangler `[dev]` settings keep the request host at `localhost:8787` over HTTP. Without this explicit override, Wrangler can infer the production host from `routes`, causing the local authentication origin check to reject requests.

For local frontend configuration, set `PUBLIC_REMADE_API_BASE_URL=http://localhost:8787/api/v1` in `apps/frontend/remade-wiki/.env` and run `pnpm dev` in a second terminal. Alternatively, run `PUBLIC_REMADE_API_BASE_URL=http://localhost:8787/api/v1 pnpm dev` and visit **localhost**, rather than 127.0.0.1. D1 state persists under `.wrangler/`. If your local database already applied the former combined `0001_init_auth.sql`, the split initial migrations require a fresh local database. Preserve any local data you need before resetting it; do not apply these rewritten initial migrations over an existing production schema. Only paired HTTP localhost origins enable development cookie names and omit Secure; production never uses this policy.

`just backend::check` checks Rust formatting and linting. `just backend::test` runs native Rust security tests only. Auth tests live in the frontend: `pnpm test:auth` builds the Wasm entrypoint and runs Vitest integration tests against actual workerd and local D1 with mocked GitHub responses. Unit, React and E2E auth coverage also stays in the frontend. `pnpm test` runs all four frontend suites; the auth integration suite requires the backend Rust toolchain and worker-build. CI runs frontend unit tests and native Rust checks; React, E2E and auth integration suites remain local.

## Production operator setup

No production resources or credentials are provisioned by the application or by CI. Complete these steps deliberately:

1. Register a GitHub **OAuth App**, with homepage `https://remade.wiki` and callback exactly `https://api.remade.wiki/api/v1/auth/github/callback`. No additional scopes or device flow are required. Configure `GITHUB_CLIENT_ID` as a Worker runtime variable and `GITHUB_CLIENT_SECRET` as a Worker runtime secret. These are unrelated to `REMADE_GH_APP_*` catalog credentials.
2. From `apps/backend/remade-api`, create D1 with `pnpm exec wrangler d1 create remade-db`. Export `GITHUB_CLIENT_ID`, `D1_DATABASE_NAME` and `D1_DATABASE_ID` (the returned UUID), or copy `apps/backend/remade-api/.env.example` to the ignored `.env` in that directory and fill them in. Run `just backend::configure` to generate ignored `wrangler.generated.toml`. The binding remains `DB`; `wrangler.toml` retains safe local defaults. Wrangler does not interpolate shell variables in TOML, so the generator writes validated deployment values explicitly. It does not deploy or create resources. Local development continues to read `GITHUB_CLIENT_ID` from `.dev.vars`.
3. Review the table migrations in order: `0001_create_users.sql`, `0002_create_user_identities.sql` and `0003_create_user_sessions.sql` under `migrations/`. Each file keeps its table and indexes together. Then run `pnpm exec wrangler d1 migrations list DB --remote --config wrangler.generated.toml` and explicitly apply with `pnpm exec wrangler d1 migrations apply DB --remote --config wrangler.generated.toml`. Deployment does not apply migrations. Future schema changes get a new numbered file using `pnpm exec wrangler d1 migrations create DB <name> --config wrangler.generated.toml`; never edit an applied migration.
4. Store the runtime secret with `pnpm exec wrangler secret put GITHUB_CLIENT_SECRET --config wrangler.generated.toml` or the Worker's runtime settings. Configure `FRONTEND_ORIGIN=https://remade.wiki` and `API_ORIGIN=https://api.remade.wiki`. Do not put secrets in Workers Builds build variables or the frontend bundle.
5. Connect `remade-api` to this repository through **Cloudflare Workers Builds**, production branch `main`, root directory `apps/backend/remade-api`. Ensure the build image has rustup; if absent, provision it using the [official Rust installer](https://www.rust-lang.org/tools/install), then source its Cargo environment. Set the build command to `pnpm --dir ../../.. install --frozen-lockfile && rustup toolchain install 1.99.0 --profile minimal --target wasm32-unknown-unknown`. Set the non-secret Workers Builds environment variables `GITHUB_CLIENT_ID`, `D1_DATABASE_NAME` and `D1_DATABASE_ID`. Set the deploy command to `node --env-file-if-exists=.env configure-wrangler.mjs && pnpm exec wrangler deploy --config wrangler.generated.toml`. Wrangler's template build hook installs pinned worker-build and generates `build/index.js` and Wasm. Neither command applies remote migrations.
6. Attach the Worker custom domain `api.remade.wiki`, as declared in Wrangler config. Leave `remade.wiki` attached to the existing Pages project. The router exposes no other API endpoints, scheduled handlers or background jobs.
7. Worker build watch paths: include `apps/backend/remade-api/*`, `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`; exclude nothing. Root tooling is included because Wrangler comes from the shared pnpm installation. Nested matches are covered by Cloudflare's wildcard.
8. Keep the existing Pages Git integration, root build and `apps/frontend/remade-wiki/dist` output. Verify Pages watch paths include `apps/frontend/*`, `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml` and `cache/github-metadata.json`. Set frontend build variable `PUBLIC_REMADE_API_BASE_URL=https://api.remade.wiki/api/v1`, which is also the default. Only this public API base belongs in the frontend.

GitHub Actions validates the backend; it does not deploy, access production auth secrets or apply remote migrations. Its check always reports, but expensive validation runs only for backend or shared tool inputs, avoiding a pending required check on unrelated PRs.

## Security and behavior

- OAuth uses random 32-byte state and PKCE S256. A signed, ten-minute HttpOnly cookie binds state, verifier and expiry to the initiating browser. Temporary cookies are cleared after callbacks, including failures. GitHub's single-use authorization code prevents successful replay. Redirects use configured fixed origins.
- GitHub tokens exist only during the callback and are discarded after resolving the stable numeric user ID. No email is collected or used to merge accounts. Upstream responses are bounded to 64 KiB and ten seconds, and errors never expose credentials.
- D1 transactionally creates users and identities. The unique provider/ID constraint arbitrates concurrent first logins; a losing batch rolls back and reads the winner. Names can change without changing the Remade user ID.
- Session tokens contain 32 bytes from the Workers Web Crypto CSPRNG. D1 stores SHA-256 hashes only. Sessions expire after 30 days. Production cookies use `__Host-`, HttpOnly, Secure, SameSite=Lax, Path=/ and no Domain.
- `/me` returns 401 without D1 access for missing or malformed cookies. User-specific responses use `Cache-Control: no-store`. Logout requires the exact frontend Origin and rejects cross-site Fetch Metadata; CORS alone is not the CSRF defense.
- The non-secret `remade_login_hint` cookie is readable by the frontend across remade.wiki subdomains, but never grants access. Without it, anonymous page loads make **zero** auth API requests. With it, the small header island resolves the current account once on mount. An invalid session clears the hint. There is no polling or health check; API failure leaves the directory usable.
- Credentialed CORS allows only the configured frontend origin. Public catalog JSON retains its separate static export and wildcard CORS rules.

Production acceptance remains manual: test a real OAuth login and logout after DNS, Worker deployment, D1 migration and runtime credentials are configured. Check cookies, `/me`, CORS, the mobile header and zero Worker requests from a fresh anonymous browser. Local mocked-provider tests cannot prove production OAuth configuration works.
